# Power Platform Harness 2.0: architecture

Status: agreed 2026-10-28, replacing the script-based design of 2026-10-27. Work happens on
`feature/onlySkills`; nothing reaches `main` until the user says so.

## Why 2.0

[`microsoft/Dataverse-skills`](https://github.com/microsoft/Dataverse-skills) and
[`microsoft/power-platform-skills`](https://github.com/microsoft/power-platform-skills) now cover
connection setup, metadata, data, the solution lifecycle, model-driven apps, flows and PCF
scaffolding. None of them covers what this harness is for: C# plugin, Custom API, JavaScript web
resource and PCF conventions, the feature solution per branch, the Definition of Done, and adapting
to an existing project instead of retargeting it.

**Official skills supply capabilities; the harness supplies conventions.** Where an official skill
covers a task, the harness names it and adds only the convention. Where the harness deliberately
overrides an official rule, the override is a declared exception, never an implicit contradiction.

## Skills only, no scripts

The skills are markdown. The agent running a skill inspects the machine, the repository and the
environment itself, with the tools' own commands and its own knowledge, and checks anything
time-sensitive against the official source at that moment. There is no PowerShell, no catalog of
versions and no baseline to keep in sync.

The trade-off is deliberate: a deterministic script was more precise, but every tool release or
template change meant maintaining it, its JSON and its tests. Natural-language skills are less
precise and need no maintenance when tools move on.

- **No hand-written versions.** Neither the skills nor the templates state a minimum or preferred
  version. `setup-tools` decides per tool whether the installed version is supported or behind,
  from the official source, and proposes the update. A pin a project needs (the `.esproj` Sdk
  attribute, npm and NuGet packages) is still a pin: a new project looks up the latest stable
  release and pins it; an existing project keeps its own.
- **Templates stay files.** The standards are the product and must not drift with the model that
  copies them. `setup-project` copies `templates/` and replaces the `{{tokens}}`, nothing else.
  Code is not templated: the standards describe `PowerPlatform.sln`, `<Project>.Common` (with the
  `PluginBase.cs` from `pac plugin init`) and the WebResources project, and the agent creates them
  the first time they are needed.
- **Proposals, never silent changes.** Every install, update, removal, overwrite or write to
  `project.json` is shown first and runs only with the user's approval.

## Scope

- **Agents:** Claude Code, GitHub Copilot (CLI and VS Code agent mode) and Codex, plus any agent
  that implements the [Agent Skills](https://agentskills.io/specification) standard. The skill
  bodies name no agent-specific tool; `allowed-tools` is kept for Claude Code.
- **OS:** Windows only.
- **Not in 2.0:** an upgrade path for 1.x projects; declaring the official plugins in the
  project's settings; Codex permission rules.

## Skills

| Skill | Owns | Writes |
| --- | --- | --- |
| `setup-tools` | The machine: CLIs, runtimes, official skills and agent plugins | Installs, only after the user approves each one |
| `setup-project` | The repository: a new one, or the harness adopted into an existing one | Files in the repository |
| `connect` | The connections `project.json` expects: DEV, the tenant, the repository, the Dataverse MCP server | `connections` in `project.json`, after confirmation |
| `set-power-platform` | Runs the three in that order and reports once | Nothing itself |

Each skill can run on its own and checks only its own prerequisites.

### Who installs what

| Component | Owner |
| --- | --- |
| PowerShell, git, .NET SDK, Node.js, az, gh (GitHub only), the az `azure-devops` extension (Azure DevOps only), playwright-cli | `setup-tools` |
| `pac`, as the Windows installer through winget. A .NET-tool pac is proposed for removal | `setup-tools` |
| Dataverse skills, via `npx skills add microsoft/Dataverse-skills -s "*" -g`. A plugin install is accepted with a warning | `setup-tools` |
| model-apps, power-automate, Ponytail (mandatory); the other power-platform-skills plugins (on request) | `setup-tools`, through each agent's plugin CLI |
| Python, its packages, `pac auth`, the Dataverse MCP server, `.env`, `scripts/auth.py` | `dv-connect`. The harness reports and delegates |

`setup-tools` also reports duplicate installs, available updates and the default-on telemetry of
model-apps and power-automate, with its documented opt-out.

## The project

`.power-platform/project.json` is versioned, holds no secret, and is the source of truth for the
project identity and the connections it expects:

```json
{
  "harnessVersion": "2.0.0",
  "identity": {
    "projectName": "Northwind",
    "publisherUniqueName": "NorthwindConsulting",
    "publisherPrefix": "nwc",
    "coreSolution": "NorthwindCore"
  },
  "connections": {
    "dataverse": { "devUrl": "https://<org>.crm4.dynamics.com", "tenantId": "<guid>" },
    "repository": { "provider": "github", "url": "https://github.com/<owner>/<repo>" },
    "azure": { "subscriptionId": null },
    "playwright": { "session": "northwind" }
  }
}
```

- **Connections without side effects.** Every `pac` command takes `--environment <devUrl>`; nothing
  runs `pac auth select`, `az account set` or `az devops configure --defaults`. The Dataverse MCP
  server is registered with `local` scope.
- **`.env`.** `connect` compares `DATAVERSE_URL`, `TENANT_ID` and `PUBLISHER_PREFIX` with
  `project.json`, reports drift and hands the fix to `dv-connect`; it never writes `.env`.
- **Instructions.** `AGENTS.md` holds the portable harness; `CLAUDE.md` is `@AGENTS.md`. In an
  existing repository nothing is moved: an existing `AGENTS.md` gains the missing sections, an
  existing `CLAUDE.md` alone gains an `@AGENTS.md` line. Every edit is shown as a diff first.
- **Permissions.** `.claude/settings.json` turns the irreversible-operation rules into `deny` /
  `ask` / `allow`. Copilot and VS Code cannot enforce rules from the repository; there, protection
  rests on the instructions.

## Solutions

- Branch `<type>/<kebab-description>`, feature solution `<type>_<PascalDescription>`, at most 65
  characters, version `1.0.0.0`, under the project's publisher. `docs/development/solutions.md`
  states the rule and the checks the agent runs before creating anything (branch free here and on
  origin, DEV reached and not production or test, publisher and prefix as expected, solution name
  free); then `git switch -c` and `dv-solution`.
- Each branch exports its feature solution to `solutions/<feature solution>/` before its pull
  request. The core solution is exported only from the trunk.
- Promotion to test or production stays with a human or a pipeline.

## Exceptions

`docs/agents/skill-exceptions.md` in every project lists each official rule the harness overrides,
quoted verbatim. After installing or updating official skills, `setup-tools` checks that each quote
still appears; a missing quote marks the exception stale, and the official rule applies until it is
updated.

| Id | Overrides | Harness rule |
| --- | --- | --- |
| E2 | `dv-connect`: "mkdir -p solutions plugins scripts" | Code lives in `src/PowerPlatform/`; `setup-project` lays the folders out before `dv-connect` runs |
| E3 | Ponytail: "leaves one small test or an assert-based self-check" | The testing rules and the Definition of Done prevail |
| E4 | `dv-solution`: "## Push: Pack + Import" | The agent imports into the DEV in `project.json` only |

E1 (PowerShell for the harness scripts) was removed with the scripts. The ids are not renumbered.
