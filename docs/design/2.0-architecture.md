# Power Platform Harness 2.0: architecture

Status: agreed 2026-10-27. This branch implements it phase by phase. Each phase ends in one or more
commits on `feature/v2-official-skills`; nothing reaches `main` until the user says so.

## Why 2.0

The harness predates Microsoft's official agent skills. Today
[`microsoft/Dataverse-skills`](https://github.com/microsoft/Dataverse-skills) and
[`microsoft/power-platform-skills`](https://github.com/microsoft/power-platform-skills) cover
connection setup, metadata, data, solution lifecycle, model-driven apps, flows, PCF scaffolding and
more. None of them covers what this harness is for: C# plugin, Custom API, JavaScript web resource
and PCF conventions, the feature solution per branch, the Definition of Done, and adapting to an
existing project instead of retargeting it.

2.0 keeps that and stops doing the rest. **Official skills supply capabilities; the harness supplies
conventions.** Where an official skill covers a task, the harness names it and adds only the
convention. Where the harness deliberately overrides an official rule, the override is a declared
exception (below), never an implicit contradiction.

## Scope

- **Agents:** Claude Code, GitHub Copilot (CLI and VS Code agent mode) and Codex, plus any agent that
  implements the [Agent Skills](https://agentskills.io/specification) standard.
- **OS:** Windows only. winget, the pac MSI and the PowerShell scripts assume it.
- **Not in 2.0:** an upgrade path for projects scaffolded by 1.x (none exist outside testing);
  macOS/Linux; APM.

## Skills

| Skill | Owns | Writes |
| --- | --- | --- |
| `setup-tools` | The machine: CLIs, runtimes, official skills and agent plugins | Installs, only after the user approves each action |
| `connect` | The project's connections: pac/Dataverse, az, gh or Azure DevOps, the Playwright session | Auth sessions and the Dataverse helper scripts; never a global default |
| `setup-project` | The repository: scaffold a new one, or adopt the harness into an existing one | Files in the repository |
| `set-power-platform` | Runs the three in order, skipping what is already in place | Nothing itself |

Each skill checks only its own prerequisites, so a user with a ready machine goes straight to
`setup-project`. The usual order is tools, connect, project, but none of them requires the previous
one to have run.

### Self-contained skills

Every skill carries its own scripts in `skills/<skill>/scripts/` and refers to them by a path
relative to its `SKILL.md`. That is the only addressing every agent supports: `${CLAUDE_PLUGIN_ROOT}`
exists only in Claude Code, and agents that install skills as loose folders (`npx skills`) bring no
plugin root at all. Helpers shared by several scripts are copied into each skill, and a check keeps
the copies identical.

`discover.ps1` is split along the same lines: toolchain checks go to `setup-tools`, environment
checks to `connect`, repository inspection and the standards baseline to `setup-project`.

### Portable skill bodies

- Questions: closed choices go through the agent's structured question tool when it has one
  (`AskUserQuestion`, `ask_user`, `request_user_input`), otherwise a numbered list in prose. The
  skill text names neither.
- `allowed-tools` stays for the agents that honour it; nothing depends on it.
- Scripts run on Windows PowerShell 5.1 and pwsh 7.

## Who installs what

One owner per component, so two installers never fight over the same tool.

| Component | Needed for | Installed by |
| --- | --- | --- |
| PowerShell (5.1 ships with Windows; 7 preferred) | The harness scripts | `setup-tools` |
| git | Branch per unit of work | `setup-tools` |
| .NET SDK | Building and testing plugins and Custom APIs; canvas-apps MCP | `setup-tools` |
| .NET Framework runtime 4.6.2 or later | Running plugin tests. Detected, not installed: Windows 10/11 ship 4.8.x | — |
| Node.js | Web resource and PCF tests and linting; official plugin hooks and MCP servers | `setup-tools` |
| pac, Windows MSI via winget | Solutions, environment access, code generation | `setup-tools`. A dotnet-tool pac found alongside is proposed for removal |
| az | model-apps, power-automate; Azure DevOps repositories | `setup-tools` |
| az `azure-devops` extension | Azure DevOps repositories only | `setup-tools` |
| gh | GitHub repositories only | `setup-tools` |
| Python, its pip packages, the `dataverse` CLI, the Dataverse MCP | The Dataverse skills | `dv-connect`. `setup-tools` detects and reports |
| playwright-cli and its skill | Checking web resources and PCF controls in DEV forms | `setup-tools` |
| Dataverse skills | Mandatory | `setup-tools`: `npx skills add microsoft/Dataverse-skills -s "*" -g`. An existing plugin install is accepted with a warning |
| model-apps, power-automate | Mandatory | `setup-tools`, as agent plugins from the `power-platform-skills` marketplace |
| Ponytail (`DietrichGebert/ponytail`) | Mandatory: less code, fewer tokens | `setup-tools`, as an agent plugin |
| The other power-platform-skills plugins | The user's choice per project | `setup-tools`, when asked |

`setup-tools` acts on the agent running it and offers the others whose CLI it finds
(`claude plugin install`, `copilot plugin install`, `codex plugin add`). Codex needs the user to
trust plugin hooks in `/hooks`; the Codex IDE extension has no plugin support, which the skill
states instead of trying.

It also reports, and offers to fix: duplicate installs of the same skills, available updates, and
the default-on telemetry in model-apps and power-automate, with its documented opt-out. Updates are
detected read-only, the way the installers themselves decide: the `skillFolderHash` in
`~/.agents/.skill-lock.json` against the folder's hash in the source repository's git tree, and an
installed plugin's version against its `plugin.json` on the marketplace's default branch. `npx skills
check` is not used: in skills 1.7.4 it is an alias of `update` and installs what it finds. The
proposed fixes are `npx skills update <skills> -g -y` and the agents' `plugin update`.

### Versions

The catalog is the single source of minimum versions. Each entry records where its minimum comes
from: an official document (pac above 2.10.0 for model-apps, Node 18 for power-automate, .NET 10
SDK for canvas-apps) or the **harness policy** of using a stable, non-obsolete release (.NET 8
minimum / 10 preferred, Node 22.13 minimum / 24 preferred). A minimum with neither is not stated.

### Why not APM, and why not plugin `dependencies`

- **APM** (`microsoft/apm`, v0.35) would be a third installer next to agent plugins and
  `npx skills`. It does not install pac, az, node or dotnet. At the time of writing it writes
  resolved secrets in plaintext to a project `.mcp.json` with the Claude target (issue #3252),
  deploys Claude-plugin skills without their namespace so one can overwrite another (#1120), and
  its manifest spec is a working draft. Reassess at 1.0.
- **`dependencies` in `plugin.json`** is a Claude Code feature only, and it installs without asking,
  which would override a user who already has the Dataverse skills from `npx skills`.

## The project

### `.power-platform/project.json`

Versioned, and holds no secret. It is the source of truth for what the project expects; `connect`
validates live sessions against it, and the generated docs carry the same values already
substituted. Draft shape:

```json
{
  "harnessVersion": "2.0.0",
  "identity": {
    "projectName": "Northwind",
    "publisherUniqueName": "NorthwindConsulting",
    "publisherPrefix": "nwc",
    "coreSolution": "NorthwindCore"
  },
  "connections": {
    "dataverse": { "devUrl": "https://<org>.crm4.dynamics.com", "tenantId": "<guid>" },
    "repository": { "provider": "github", "url": "https://github.com/<owner>/<repo>" },
    "azure": { "subscriptionId": null },
    "playwright": { "session": "northwind" }
  }
}
```

`provider` is `github` or `azure-devops`; it decides whether `gh` or `az devops` is needed, and
which one the generated instructions name.

`dv-connect` keeps its own `.env` (gitignored). `connect` compares `DATAVERSE_URL`, `TENANT_ID` and
`PUBLISHER_PREFIX` with `project.json`, reports any drift and hands the fix to `dv-connect`; it
never writes `.env` itself. `SOLUTION_NAME` changes per branch and is not compared.

### Connections without side effects

Validating a session means checking it points at the environment, tenant, account or repository
`project.json` names, not just that one exists. Nothing changes a default another project relies on:

- pac: every command takes `--environment <devUrl>`; `pac auth select` is never needed.
- az: `--subscription`, `--org` and `--project` on each command, never `az account set` or
  `az devops configure --defaults`.
- Dataverse MCP: registered with `local` scope (this user, this project, not versioned).
- Playwright: the browser profile lives in
  `%LOCALAPPDATA%\power-platform-harness\<project>\playwright`, outside the repository; the
  repository holds only a `.playwright/cli.config.json` without secrets that points there.

`connect` also makes sure `scripts/auth.py` and `scripts/enable-mcp-client.py` exist, following
`dv-connect`'s own procedure. Installed through `npx skills`, the Dataverse skills download them
from the default branch of their repository, unpinned; they are **committed**, so a change to
authentication code is reviewed like any other.

### Instructions

| File | Content |
| --- | --- |
| `AGENTS.md` | The portable harness: description, the mandatory pointer to `docs/agents/development-standards.md`, tool usage, the pointer to the exceptions. Read natively by Codex, Copilot and VS Code |
| `CLAUDE.md` | `@AGENTS.md` plus anything only Claude Code uses. Claude Code reads `AGENTS.md` only when there is no `CLAUDE.md` |

`AGENTS.md` stays a short set of pointers: Codex caps the instructions it loads at 32 KiB. The
per-technology standards are reached through the index in `development-standards.md`, as in 1.x.

In an existing repository nothing is moved: an existing `AGENTS.md` gains the harness section; an
existing `CLAUDE.md` alone gains an `@AGENTS.md` line and a new `AGENTS.md`. Every edit is shown as
a diff before it is written.

### Official plugins declared in the project

`setup-project` declares model-apps, power-automate and Ponytail in `.claude/settings.json` and
`.github/copilot/settings.json` (`extraKnownMarketplaces`, `enabledPlugins`). Copilot CLI installs
them for the repository from that; Claude Code only enables what is already installed, which is why
`setup-tools` installs them too. The Dataverse skills are not declared: they come from `npx skills`,
and declaring the plugin would show "enabled but not installed" to everyone who has them that way.

### Permissions

One table in the scaffold generates both enforceable forms:

- Claude Code: `deny` / `ask` / `allow` in `.claude/settings.json`.
- Codex: `forbidden` / `prompt` rules in `.codex/rules/harness.rules`, loaded once the project is
  trusted.

Copilot CLI and VS Code cannot enforce a rule from the repository: Copilot's repository settings
take no permission keys, and VS Code's terminal auto-approve rules ask rather than block and are
documented as no security boundary. There, protection rests on the instructions and on scripts that
check before they act. The README states this limitation.

## Solutions

- **Creating a feature solution** is delegated to `dv-solution`. The naming stays the harness's:
  branch `<type>/<kebab-description>`, solution `<type>_<PascalDescription>`, at most 65
  characters, version `1.0.0.0`, under the project's publisher.
- **`scripts/new-feature.ps1`** shrinks to what must be deterministic and works the same in every
  agent: derive both names, check the branch is free locally and on the remote, check pac points at
  an environment that does not look like production or test, check the publisher exists with the
  expected prefix and the solution name is free, then create the branch or worktree and print the
  solution name for `dv-solution`. It no longer creates the solution.
- **Export, unpack and commit** follow `dv-solution`: each branch exports its feature solution to
  `solutions/<feature_X>/` before its pull request, so the review diff shows what the branch
  touched. The core solution is exported only from the trunk, as an explicit operation: exporting
  it from a shared DEV would capture colleagues' unfinished work. `solutions/` sits at the
  repository root, next to `src/`; generated source and hand-written code stay apart.
- **Promotion** to test or production stays with a human or a pipeline (exception E4).

## Exceptions

`docs/agents/skill-exceptions.md` in every project lists each official rule the harness
deliberately overrides, and `AGENTS.md` points at it. An exception exists only because the user
declared it: a harness text that happens to contradict an official skill is a bug to fix, not an
exception to add.

Each entry carries an id, the official skill, the **verbatim quote** of the rule it overrides, the
harness rule, its scope and the reason. Discovery checks that every quote still appears in the
installed skill, the same way it checks the standards baseline: an official rule that changed marks
its exception stale instead of letting it silently override something new.

| Id | Overrides | Harness rule |
| --- | --- | --- |
| E1 | `dv-overview`: "Python is the language for automation **logic**" | The harness's own scripts are PowerShell. New project scripts follow the official rule |
| E2 | `dv-connect`: "mkdir -p solutions plugins scripts" | Code lives in `src/PowerPlatform/`, not `/plugins/`. `setup-project` runs before `dv-connect`'s workspace step |
| E3 | Ponytail: "leaves one small test or an assert-based self-check" | Testing and the Definition of Done in `development-standards.md` prevail over Ponytail's test minimalism. Ponytail governs the rest |
| E4 | `dv-solution`: "## Push: Pack + Import" | The agent writes and imports into the DEV environment in `project.json` only |

## Template content

| Kept | Delegated or removed |
| --- | --- |
| Design principles, business logic separation, error handling, data and secrets, testing (test-first, with the tests written by a subagent), Definition of Done, git | `toolchain.md` install commands and Dataverse MCP setup (to `setup-tools` / `dv-connect`; the 1.x `dotnet tool install … Dataverse.MCP` is obsolete) |
| `javascript.md`, `webresources-project.md`, `csharp-plugins.md`, `custom-apis.md`, `pcf.md` | The how of inspecting metadata in `dataverse-schema.md` (to `dv-metadata`) |
| Schema conventions in `dataverse-schema.md` | Creating solutions with pac and "export is out of scope" in `solutions.md` (to `dv-solution`) |
| Feature solution per branch, the solution table, permissions | |

"Never simulate metadata" and "name the environment" stay, with a pointer to `dv-overview`, which
says the same.
